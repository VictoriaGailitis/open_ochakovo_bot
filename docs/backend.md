# Сервер VK Mini App «Очаково: изнутри»

Python 3.10+; зависимости отсутствуют. SQLite сохраняет профиль, сессии, черновики, завершения заданий, реестр баллов, отклики, записи на события, активности с QR, историю их выполнения и обмены. Каталог — `server/catalog.json`. Все карьерные предложения, события, награды и профессиональные модели демонстрационные; реального найма или обещания выдачи награды нет.

## Локальный запуск

Из корня проекта:

```sh
DEV_AUTH=1 ALLOWED_ORIGINS=http://localhost:5188,http://127.0.0.1:5188 python3 -m server --host 127.0.0.1 --port 3001
```

Фронтенд направляет `/api` на этот сервер через Vite proxy. `DEV_AUTH=1` разрешает демонстрационный вход только с loopback IP. По умолчанию он выключен. Демопользователь имеет namespace `demo:`, VK-пользователь — `vk:`; их данные не смешиваются.

В VK требуется серверная конфигурация:

```sh
VK_APP_ID=<application-id> VK_APP_SECRET=<secure-key> ADMIN_TOKEN=<private-HR-token> python3 -m server --host 127.0.0.1 --port 3001
```

Не передавайте VK_APP_SECRET и ADMIN_TOKEN во frontend env. Клиент отправляет исходный `window.location.search` как `launchParams`. Сервер сортирует только `vk_*`, кодирует `urlencode`, проверяет HMAC-SHA256 через constant-time comparison, ID приложения и `vk_ts` (TTL по умолчанию 3600 секунд, настраивается `VK_LAUNCH_TTL`; допускается 60 секунд рассинхронизации часов). Требуется положительный `vk_user_id`. Повторяющиеся параметры отклоняются. Алгоритм соответствует [официальному примеру VKCOM](https://github.com/VKCOM/vk-apps-launch-params/blob/master/examples/python3.py).

При доступе по публичному HTTPS-домену используйте reverse proxy: `/api` → Python server, остальное → собранный frontend. Не публикуйте stdlib development HTTP server непосредственно в интернет. Для production задайте DEV_AUTH=0, HTTPS, разрешённые домены ALLOWED_ORIGINS и политику хранения персональных данных. В VK нужно самостоятельно зарегистрировать приложение и указать HTTPS URL — наличие веб-прототипа не подтверждает настройку платформы.

`--db` меняет путь хранилища. По умолчанию `.data/ochakovo.sqlite3`. Схема расширяет существующие таблицы без удаления данных. WAL и `BEGIN IMMEDIATE` предотвращают одновременное двойное начисление, перерасход баланса и превышение мест/запасов. Не копируйте работающую SQLite-базу без согласованного snapshot/backup.

## Формат запросов

`Content-Type: application/json`, `Authorization: Bearer <session-token>`; срок сессии — 24 часа. В базе сохраняется SHA256-хеш токена. Лимит тела 128 KiB, черновика 64 KiB. Ответы `Cache-Control: no-store`.

Ошибка: `{error: string, code: string, details?: object}`. Ошибки полей профиля — HTTP422 с `code:"validation_error"` и `details: {field: message}`. Валидная дата рождения с возрастом младше 18 лет возвращает отдельный HTTP422 `{error:"Регистрация доступна с 18 лет…",code:"age_restricted",details:{birthDate:"…"}}`, чтобы клиент показал приглашение вернуться позже. Неверное игровое решение — HTTP200 и `correct:false`; оно не создаёт завершение или начисление. Ресурсы другого пользователя не выдаются.

Профиль: `{fullName,contact,birthDate:'YYYY-MM-DD',direction,availability,education,schedule?,consent:true,futureContact?:false}`. Контакт — телефон или email. Все основные текстовые поля обязательны. Для этого прототипа принимается возраст от 18 до 100 лет. Возраст рассчитывается по московской календарной дате (UTC+3), ровно в восемнадцатый день рождения регистрация разрешена. Дата рождения принимается только в каноническом ISO-формате `YYYY-MM-DD`: невозможная дата, будущая дата, дополнительные пробелы, basic/week ISO-формы и дата со временем возвращают `validation_error`, а не `age_restricted`. Для родившихся 29 февраля возраст в невисокосном году увеличивается 1 марта, по сравнению календарных месяца и дня. Отказ не сохраняет неполный профиль, не изменяет ранее сохранённый взрослый профиль и не создаёт постоянный бан после ошибочного ввода; дату можно исправить и отправить анкету повторно. Пока профиль не сохранён, отклики и игровые действия недоступны (`profile_required`). При сохранении сервер добавляет `consentedAt`. Согласие на будущие предложения независимо от обработки анкеты. Для игр, откликов, событий и наград нужен сохранённый профиль; баланс и завершения не являются условиями отклика.

`progress`: `{task,draft,completed:string|null,revision:number}`. Черновики имеют монотонную версию: клиент передаёт `revision = max(Date.now(), lastRevision + 1)` и начинает счётчик с максимума полученных `progress[].revision`. Запрос с меньшей версией не меняет базу и возвращает HTTP200 `{saved:false,reason:"stale",draft,revision}` с текущим серверным состоянием. Это предотвращает затирание свежего черновика поздним autosave/pagehide-запросом. Старым клиентам без revision сервер присваивает `max(now_ms,stored+1)`; завершение задания версию черновика не сбрасывает. Существующая схема обновляется добавлением draft_revision с начальным значением0 без удаления данных. `ledger`: `{id,reason,delta,created}`. Отклик содержит snapshot профиля на момент отправки. Для совместимости отклики имеют и `offer`, и `offerId`; записи `event`/`eventId`, обмены `reward`/`rewardId`. Один пользователь может отправить один отклик на предложение, иметь одну активную запись на событие и обменять каждую награду один раз. Отменённую запись можно восстановить при наличии мест. Время события — Москва (UTC+3).

За каждое содержательно завершённое задание/уровень баллы начисляются один раз. Перепрохождение и обновление черновика завершение не сбрасывают. За отклики, профиль и аналитику баллы не начисляются. Обмен и отрицательная запись ledger совершаются в одной транзакции, после проверки баланса и остатка награды. Нет клиентского API для произвольного начисления.

## Игровые форматы

Задачи: `shift-1..2`, `signal-1..3`, `movement-1..3`, `lab-1..3`, `delivery-1..3`, `history-1` — 15 завершённых учебных раундов. «Разберись в смене» имеет два причинно различных варианта на одном исследовательском пульте.

- **signal**: `{rules:[{condition:'red'|'blue'|'marked'|'unmarked'|'red_marked'|'always',output:'left'|'right'}]}`. До трёх блоков, первое совпадение определяет выход. Сервер проверяет все комбинации цвета/метки, включая невидимые примеры.
- **movement**: `{gears:[{x,y}]}`. Координаты целочисленные; привод и цель уже стоят на поле, повторно их передавать не нужно. Соседние по стороне колёса меняют направление. Все детали должны быть в границах, соединены, не пересекаться, а цель — вращаться как указано. Несколько конструкций допустимы.
- **lab**: `{sampleId,evidence:['color','acidity',...]}`. Результаты выбранных исследований должны оставить ровно один подходящий образец в матрице. Вымышленные вещества и условные исследования явно обозначены.
- **delivery**: `{placements:[{batchId,x,y,rotated:boolean}],route:[{x,y}]}`. Проверяются точный комплект, запрет резервированных и повторных партий, геометрия и непересечение. Маршрут начинается в `puzzle.start`, идёт по соседним клеткам и проходит через точки всех выбранных партий. Поворот меняет `(dx,dy)` на `(dy,dx)`.
- **history**: `{answers:{founded:'1978',event:'olympics',brand:'secret'}}`. Три вопроса об истории предприятия/бренда; [официальная история «Очаково»](https://ochakovo.ru/en/istoriya/) проверена 24.10.2026. Факты: открытие 18.12.1978; подготовка к Олимпиаде-80; белый квас «Семейный секрет», 2013.

## Симулятор «Разберись в смене»

Это исследование причин изменения выпуска: 12 показателей, график каждого показателя, схема соседних участков, журнал с деталями событий, независимые проверки, собственные наблюдения, структурированный вывод и разбор результата. Заранее правильные карточки не выделяются. Показатели, последовательность и нормы — учебная модель, не производственная инструкция.

`shift-1`: выпуск 42 вместо 60 упак./мин при прежней подаче 60; перед упаковкой растёт очередь. `shift-2`: тот же выпуск 42 связан с сокращением подачи с предыдущего участка; очередь иссякает, действующая настройка упаковки остаётся 60. Таким образом, повтор не решается механическим переносом прошлого ответа. Подготовительный и аварийный варианты в этот объём не включены.

Публичный `puzzle` содержит `scenarioId`, `snapshotTime`, `measurementWindow`, `modelNote`, `metrics[12]`, `scheme:{nodes,flows}`, `journal`, `checks`, `facts`, `conclusion`, `hints` и `maxObservations:32`. Показатель имеет `value`, `previous`, `unit`, `series:[{time,value}]`, `factId` и `historyFactId`. Графики содержат шесть дискретных снимков с неравными интервалами вокруг 14:06:40; X-координата рассчитывается по времени. Темпы нормированы на минуту в момент снимка, без обещания скользящего среднего за последние 60 секунд. В первом раунде сначала падает темп упаковки, затем выход/сигналы и растёт очередь. Во втором сначала сокращается подача, затем укупорка, упаковка и выход; очередь иссякает. Последняя точка каждого графика совпадает с текущим значением показателя. Каждый материал ссылается на канонический факт `{id,source,time,text}`. Журнал хранит обычные события наряду со значимыми; неподтверждённое предположение коллеги не приравнивается к результату проверки.

Черновик сохраняет `observations:[{factId,source,time,fact,note}]`, `hypothesis` и UI-состояние. Для известных factId сервер берёт source/time/fact из каталога, сохраняет пользовательскую note без смысловой оценки. До 32 разных наблюдений; заметка до 2 000 символов, гипотеза до 4 000. Можно удалять, заменять и редактировать заметки. Открытие материалов баллов не даёт, список наблюдений автоматически правильными фактами не заполняется.

Решение:

```json
{
  "observedChange": "claim-id",
  "explanation": "explanation-id",
  "evidence": ["canonical-fact-id"],
  "nextStep": "action-id",
  "responsible": "role-id"
}
```

Текстовые варианты конструктора публикуются в `puzzle.conclusion`, однако принятые соответствия, категории достаточности и разбор остаются в `server/shift.py` и не передаются в публичный каталог. Основания выбираются из уже сохранённых собственных наблюдений, поэтому перед complete клиент сохраняет актуальный draft. Свободные заметки и гипотеза помогают осмыслению, но сервер не обещает оценивать их естественный язык.

Сервер проверяет локализацию, причинную связь, достаточность и непротиворечивость фактов, следующий шаг и ответственного. Принимаются разные достаточные пути: например, темп упаковки + динамика очереди + деталь журнала или схема потока + запись настройки + независимое подтверждение. Достаточность определяется категориями доказательств, без обязательного точного набора или числа карточек. Нормальные сопутствующие факты не штрафуются. Поддельные factId, несовместимое объяснение и неподтверждённая гипотеза в качестве доказательства отклоняются. Самостоятельное повышение лимита, обход датчика или перезапуск не принимаются как действие игрока.

За завершение каждого нового варианта начисляется 30 баллов один раз: 10 за обоснованную локализацию, 10 за причину и 10 за согласованный следующий шаг. Частичная попытка баллы не начисляет; ответ можно исправить без штрафа за время или подсказку. Успешный completion дополнительно содержит `assessment:{localization:10,cause:10,nextStep:10}`, `explanation` и `outcome:{summary,before,after}`. Последствия описывают согласованные действия команды в учебной модели; игрок не ремонтирует и не запускает оборудование самостоятельно.

Проверки в `server/tests/test_shift.py` покрывают разные достаточные пути и нейтральные дополнительные факты, недостаточные/поддельные/противоречащие основания, действия вне полномочий, сохранение и канонизацию наблюдений, собственные основания, другой причинный вариант при том же симптоме, конкурентные начисления и отсутствие приватных правил в публичном puzzle.

## Активности мероприятий и QR

Каждое мероприятие содержит публичный массив `activities:[{id,eventId,title,description,points,active}]`. Это небольшие задания внутри встречи, экскурсии или мастер-класса. Каталог содержит только демонстрационные seed-описания: по две активности на каждое из трёх событий. Источник актуальных определений — SQLite `event_activities`; перезапуск сохраняет существующие определения, деактивацию и приватные QR-токены.

При первом добавлении каждой активности сервер создаёт уникальный `qr_token` из 32 случайных байтов (`secrets.token_urlsafe(32)`, 43 символа URL-safe алфавита). QR содержит payload `ochakovo:activity:v1:<opaqueToken>`. Токен и готовый payload не сохраняются в Git-каталоге, не выдаются публичным `/api/catalog` или `/api/bootstrap`, не передаются в URL и не пишутся в access log. Создание активностей и выдача/скачивание QR для организаторов будут частью отдельной будущей админки и сейчас не реализованы. Текущий API не выдаёт готовые приватные payload. QR остаётся стабильным; доступность определяется `active` в хранилище.

Сканирование: `POST /api/event-activities/scan` с `{code:"ochakovo:activity:v1:<opaqueToken>"}` и сессией пользователя. Нужен сохранённый профиль; предварительная запись на мероприятие не требуется. Сканирование не создаёт регистрацию, не расходует места и не меняет остальные записи.

Ответ:

```text
{
  activity: {id,eventId,title,description,points,active},
  event: {id,title},
  completion: {activityId,eventId,completedAt,awardedPoints},
  pointsAwarded: number,
  alreadyCompleted: boolean,
  balance: number
}
```

`activityCompletions` в bootstrap содержит `{activityId,eventId,completedAt,awardedPoints}` только текущего пользователя. `awardedPoints` — сохранённая сумма первоначального начисления, даже если размер начисления в определении активности позже изменится. При повторном сканировании `pointsAwarded:0`, `alreadyCompleted:true`; исходные completion и баланс не меняются. Баллы берутся только из серверного определения, клиент не может назначить сумму.

В одной транзакции создаются уникальный `activity_completions(user_id,activity_id)` и положительная запись ledger с reason `event-activity:<activityId>`. Конкурентные повторы не создают новых баллов, ошибка ledger откатывает completion целиком. Таблицы добавляются без удаления существующих профилей, игровых завершений, сессий или истории. Код фиксирует предъявление QR в прототипе; он не доказывает физическое присутствие на площадке.

Ошибки: `400 qr_invalid` — неверный/чужой формат; `404 activity_not_found` — payload правильной формы, но токен не найден; `409 activity_inactive` — активность отключена; `409 profile_required` — профиль не сохранён; `401 unauthorized` — нет действующей сессии. Отключённая активность не принимается даже после прежнего выполнения; история выполнения при этом сохраняется.

Баллы в хранилище ограничены целыми значениями от 1 до 1 000. Возможное последующее изменение определения активности влияет только на будущие первые выполнения; исторические awardedPoints и ledger не переписываются. API управления активностями, экран организатора и команды управления QR в этом объёме отсутствуют. Существующий HR-кабинет работает с откликами, как и прежде.

`server/tests/test_activities.py` проверяет additive migration старой базы, стабильность приватных токенов после перезапуска, отсутствие QR в публичных ответах, разграничение ошибок, необходимость профиля, walk-in без расхода мест, конкурентные повторы, изоляцию пользователей, сохранение баланса, неизменность заработка при изменении определения и откат completion при ошибке ledger. Тестовые payload получают напрямую из отдельной временной SQLite-базы; состояние inactive и изменённые баллы подготавливаются SQL-фикстурами. Это не пользовательский API или CLI управления. HTTP-тест проходит сканирование, повторное выполнение и получение истории; отдельно проверяется отсутствие organizer endpoints и сохранение прежнего HR-поведения.

## HR и аналитика

Защищённые запросы используют `X-Admin-Token: <ADMIN_TOKEN>` или `Authorization: Bearer <ADMIN_TOKEN>`. Токен нельзя включать в URL или распространять среди кандидатов. CLI берёт его из ADMIN_TOKEN; при отсутствии использует игнорируемый `.data/admin-token`, при отсутствии файла создаёт его с правами 0600. Содержимое не выводится в журнал.

- `GET /api/admin/applications` → `{applications,demo:true}`.
- `PATCH /api/admin/applications/:id` с `{status:'sent'|'reviewing'|'contacted'|'accepted'|'rejected'}`.
- `GET /api/admin/analytics` → агрегированные события, число профилей и откликов. Это наблюдения прототипа, не доказательство роста конверсии.

Клиентские события ограничены allowlist: onboarding_started, profile_form_opened, offer_viewed, task_opened, task_started, task_hint, event_viewed, reward_viewed, application_reviewed. Профиль, сессия, отклик, завершение игры, запись/отмена и обмен фиксируются сервером. Аналитика не принимает произвольные персональные поля.

## Проверка

```sh
python3 -m unittest discover -s server/tests -v
```

Тесты используют отдельную временную базу, не меняют пользовательскую `.data`. Проверяются все 15 решаемых уровней, неверные решения, сохранение после нового подключения, изоляция пользователей, профиль и согласие, реальный HTTP-путь отклика, HR-статус, VK HMAC/подмена/срок/ID, запрещённый dev-вход, параллельное повторное завершение, обмен и конкурентная запись сверх лимита, конкурентные черновики с переставленными версиями и миграция старой схемы без потери прогресса.

## Сборка и развёртывание

После `npm run build` сервер также отдаёт `dist/index.html`, статические ассеты и SPA fallback для клиентских маршрутов. `npm start` обслуживает собранное приложение и `/api` с одного origin. Только файлы внутри dist доступны клиенту: `.data`, `.env`, серверный исходный код и traversal-пути не выдаются. HTML не кэшируется надолго, хешированные Vite assets имеют immutable cache. `DIST_DIR` позволяет указать другой каталог сборки.

Файл `.env.example` документирует переменные; Python автоматически `.env` не загружает. Передайте их через shell, секреты платформы или Docker `--env-file`.

```sh
docker build -t ochakovo-miniapp .
docker run --rm --name ochakovo-miniapp --env-file .env -p 127.0.0.1:3001:3001 -v ochakovo-data:/app/.data ochakovo-miniapp
```

Контейнер запускается от непривилегированного UID10001, хранит базу в постоянном volume, содержит только Python runtime и готовые frontend assets. VK_APP_ID, VK_APP_SECRET и ADMIN_TOKEN передаются при запуске; они не попадают в образ. Dockerfile и контейнер не настраивают домен, TLS, VK developer account или реальный HR-маршрут компании. Перед обратным proxy оставляйте DEV_AUTH=0. Демовход дополнительно запрещён для нелокального Host и при forwarded-заголовках: loopback-адрес proxy не должен становиться доказательством локального пользователя.

`bootstrap` содержит `routeCompleted:boolean` и `routeProgress:{completed,total,taskIds,completedTaskIds}` для первых уровней пяти игр (включая shift-1) и исторического теста, всего шесть заданий. Ранее начисленные баллы и завершения сохраняются; приглашение теперь учитывает новое исследование смены. Это основание показать приглашение на экскурсию. Возможность записаться через календарь не зависит от этого флага или баллов.

## Клиентский QR-сканер

Внутри VK используется `VKWebAppOpenCodeReader` с ответом `code_data` ([официальный SDK](https://github.com/VKCOM/vk-bridge)). Для веб-камеры и локальных изображений используется [ZXing browser](https://github.com/zxing-js/browser): динамическая загрузка только при выборе способа распознавания, камера с предпочтением задней, явное освобождение tracks/decoder/object URL при остановке, скрытии и выходе. Версии 0.1.5/0.21.3 совместимы с текущим Node 20/22; новые ветки требуют Node 24. `qrcode` — только dev-зависимость для тестовых QR, без интерфейса генерации в приложении.

Камера запрашивается только после нажатия пользователя. Изображения PNG/JPEG/WebP до 10 MiB читаются локально; на API отправляется только распознанный payload. Чужие URL и команды не открываются. После ошибки можно повторить проверку. Повторный кадр блокируется синхронно до ответа API; серверная уникальность остаётся обязательной. После принятого ответа приложение обновляет статус, баланс и историю; QR не передаётся через URL.


## Материалы, медиа и сообщество

- `GET /api/materials`, `GET /api/materials/:id`, `POST /api/materials/:id/complete`: сессия, серверная аудитория, закрытые ответы и однократная награда. Кандидату для начисления нужна сохранённая анкета; сотруднику — активный выданный аккаунт.
- `GET /api/community/bootstrap`: только действующая staff-сессия, собственные баллы/операции/записи и события `staff/all`. Публичный каталог показывает только `candidate/all`.
- Защищённые `GET/POST /api/admin/events`, `GET/PUT/PATCH/DELETE /api/admin/events/:id`: определения событий, аудитория, публикация; DELETE архивирует. QR-активности сохраняют прежние ID/токены. Интерфейс управления активностями и скачивания QR остаётся задачей отдельной админки.
- `POST /api/admin/media`: бинарное тело PNG/JPEG/WebP/MP4/WebM, максимум 50 МиБ; `Content-Type` задаёт MIME, `X-Media-Audience` — candidate/staff/all, необязательный `X-File-Name` — имя. HR-ключ проверяется до чтения большого тела. Метаданные доступны через `GET /api/admin/media`, предпросмотр — `GET /api/admin/media/:id`.
- `GET /api/media/:id`: только Authorization Bearer, активная staff-сессия для внутренних файлов, ссылка на файл из опубликованного неархивного материала подходящей аудитории. Не добавляйте токены в URL. Клиент загружает Blob и освобождает object URL. Файлы до 50 МиБ полностью загружаются перед воспроизведением; потоковое хранилище/CDN остаётся будущим расширением.
- Медиа хранится BLOB в `material_media`, вместе с основной БД. Добавьте объём медиа в расчёт места и резервных копий. Файлы не публикуются в dist/public. Нет публичного доступа к черновикам, HTML/SVG-upload не поддерживается.
