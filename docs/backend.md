# Сервер VK Mini App «Очаково: изнутри»

Рабочий сервер — Django 5.2 LTS с Django Unfold и PostgreSQL 16. Мини-приложение, API `/api/` и персональная админка `/admin/` используют одну базу. Python-зависимости закреплены в `requirements.txt`; для локального запуска используется Python 3.13. SQLite сохранён как источник однократной миграции и изолированная реализация для legacy-тестов. В рабочем runtime SQLite не открывается и резервного перехода к нему нет.

## Подготовка и запуск

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/setup-local.py
npm ci
npm run dev
```

Нужен запущенный Docker. Локальный PostgreSQL доступен только на `127.0.0.1:55432`; данные сохраняются в `open_ochakovo_pgdata`. Скрипт создаёт игнорируемые `.env` и `.data/postgres.env` с локальными секретами. `npm run dev` выполняет `scripts/prepare_dev.py`, затем запускает Django на 3001 и Vite на 5188. Подготовка применяет миграции, при первом запуске переносит совместимую старую `.data/ochakovo.sqlite3` в пустую базу, добавляет отсутствующий seed и создаёт локального администратора. Доступ к нему находится только в `.data/django-local-admin.json`.

Для отдельной подготовки или запуска собранного интерфейса:

```sh
npm run admin:prepare
npm run build
npm start
```

`npm start` — development server Django, не production-процесс. Он читает `.env`, поэтому созданный локальным setup `DEV_AUTH=1` остаётся включённым. Production Compose запускает Gunicorn с `DEV_AUTH=0`, `DJANGO_DEBUG=0` за Caddy. Полные процедуры: [админка и перенос](django-admin.md), [VK-размещение](vk-deployment.md).

## Настройки

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Обязательный PostgreSQL URL; SQLite URL отклоняется |
| `SECRET_KEY` / `DJANGO_SECRET_KEY` | Django secret длиной не менее 50 символов |
| `DEV_AUTH` | Только локальная демонстрация; в production 0 |
| `DJANGO_DEBUG` | В production 0 |
| `DJANGO_ALLOWED_HOSTS` | Разрешённые имена сайта без схемы |
| `CSRF_TRUSTED_ORIGINS` | HTTPS origins персональной админки |
| `DJANGO_TRUST_PROXY` | Доверять `X-Forwarded-Proto` только за собственным proxy |
| `VK_APP_ID`, `VK_APP_SECRET` | ID и защищённый ключ приложения VK, только сервер |
| `VK_LAUNCH_TTL` | Допустимый возраст параметров запуска, по умолчанию 3600 секунд |
| `ALLOWED_ORIGINS` | Дополнительные origins API; при одном origin не нужны |
| `DJANGO_TEST_DATABASE_NAME` | Отдельное имя тестовой PostgreSQL-базы, например `test_ochakovo_ci` |

`.env` загружается автоматически без подстановки команд; явные переменные процесса имеют приоритет. Только при `DEV_AUTH=1` отсутствие Django secret компенсируется случайным `.data/django-secret` с правами 0600. Production требует явно заданный secret. Значения с ключами не должны попадать в `VITE_*`, исходники, URL, Git или журнал запросов.

Кандидат входит через подписанные параметры VK. Клиент передаёт исходный `window.location.search` как `launchParams`. Сервер сортирует `vk_*`, проверяет HMAC-SHA256 постоянным по времени сравнением, ID приложения, положительный `vk_user_id`, `vk_ts` и срок запуска; повторяющиеся параметры отклоняются. Допускается 60 секунд рассинхронизации часов. Демовход с `devUserId` разрешён только при явном `DEV_AUTH=1`, loopback-адресе и локальном Host, без forwarded-заголовков. Идентификаторы разделены на `demo:`, `vk:` и выданные staff-аккаунты.

## Хранение и транзакции

Django ORM и миграции управляют схемой PostgreSQL. В `backoffice/core/` сохранены 31 таблица прежнего домена с точными SQL-именами и столбцами. JSON и timestamps старой модели остаются TEXT, флаги — INTEGER, бинарные медиа — BYTEA. Для старых составных ключей добавлены технические PK при сохранении прежней уникальности; у вопросов материала прежний `id` остаётся ID вопроса, технический PK называется `_pk`. Дополнительные модели содержимого и административного аудита находятся в `content` и `operations`.

`server/postgres.py` адаптирует параметризованные SQL-сервисы к соединению и `atomic()` Django; вложенные административные операции участвуют в той же транзакции. API блокирует строку пользователя для операций с его состоянием; общие ресурсы защищены блокировками мероприятия и награды. Уникальные ограничения остаются последней защитой от повторных начислений, откликов, регистраций и обменов. Повтор запроса не создаёт вторую награду.

Текущий каталог читается из PostgreSQL: только опубликованные версии уровней активных семейств, опубликованные предложения и награды, доступные события. `LevelVersion.public_snapshot` отделён от закрытого `private_rule` и проверочных примеров. Конкретное решение проверяется по той версии правила, с которой задача была получена сервером. Файлы `server/catalog.json` и `server/level-rules.json` служат стартовыми определениями и тестовыми fixtures; настроенный runtime не подменяет ими содержимое базы.

Архивирование скрывает определение, сохраняя связанные действия. Старые баллы, завершения, снимки анкет, версии материалов и атрибуция рекомендаций не перезаписываются редакторским сохранением. Импорт SQLite требует пустых целевых таблиц, читает источник read-only и создаёт согласованную резервную копию; порядок описан в [runbook](django-admin.md#перенос-старого-прототипа).

## HTTP-контракт

Обычные запросы: `Content-Type: application/json`, `Authorization: Bearer <session-token>`. Сессия API действует 24 часа; база хранит SHA256-хеш токена. Лимиты: тело JSON 128 KiB, черновик 64 KiB, отдельная загрузка медиа до 50 МиБ. Ответы API имеют `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.

Ошибка: `{error:string,code:string,details?:object}`. Неизвестное или скрытое определение возвращает 404. Неверное игровое решение возвращает HTTP 200 с `correct:false`, без завершения и начисления. Данные другого пользователя не выдаются.

| Метод | URL | Основной контракт |
| --- | --- | --- |
| GET | `/api/health` | `{ok,service,database:'postgresql'}`; проверяется соединение |
| GET | `/api/config` | `{devAuth,vkConfigured}` |
| GET | `/api/catalog` | `{tasks,games,offers,events,rewards}`, доступные определения и остатки |
| GET | `/api/game-assets` | Активный публичный manifest спрайтов |
| GET | `/api/game-assets/:id/` | Активный бинарный ассет, без исходников и закрытых правил |
| POST | `/api/auth` | `{launchParams}` или только локально `{devUserId}` → `{token,userId,mode}` |
| DELETE | `/api/auth` | Завершить текущую API-сессию |
| GET | `/api/bootstrap` | `{user:{id},profile,balance,catalog,progress,ledger,applications,registrations,exchanges,activityCompletions,routeCompleted,routeProgress}` |
| GET / PUT | `/api/profile` | Прочитать / сохранить анкету |
| PUT | `/api/tasks/:id/draft` | `{draft,revision?}` → `{saved,revision,...}` |

| POST | `/api/analytics` | Разрешённое событие интерфейса |

Сотрудники входят через `POST /api/staff/login`; действующая роль проверяется при каждом запросе. Внутренний контент и события доступны через `/api/community/bootstrap`, материалы — через `/api/materials`, `/api/materials/:id`, `/api/materials/:id/complete`. Контракт практики и наставников — [practice.md](practice.md), материалов — [materials.md](materials.md), рефералки — [referrals.md](referrals.md).

### Анкета и возраст

Профиль: `{fullName,contact,birthDate:'YYYY-MM-DD',direction,availability,education,schedule?,consent:true,futureContact?:false}`. Контакт — телефон или email; основные текстовые поля обязательны. При сохранении добавляется `consentedAt` и факт согласия в административную историю. Согласие на будущий контакт независимо от согласия на обработку анкеты.

Возраст рассчитывается по московской календарной дате. Ровно 18 лет разрешено; корректная прошлая дата с возрастом младше 18 возвращает HTTP 422 `code:'age_restricted'`, `details.birthDate`. Невозможная, будущая или неканоническая ISO-дата возвращает отдельный `validation_error`. Для родившихся 29 февраля в невисокосном году граница наступает 1 марта. При отказе профиль не сохраняется, ранее сохранённые данные не меняются, постоянный бан не создаётся. Прототип также ограничивает возраст сверху 100 годами.

Кандидату для игровых действий, отклика, записи, QR и обмена нужна сохранённая анкета (`profile_required`). Для staff-сценариев сообщества применяется действующая выданная учётная запись. Баллы и игровой прогресс не являются условием отклика или записи на событие.

### Черновики, завершения и баллы

`progress`: `{task,draft,completed:string|null,revision:number}`. Клиент выдаёт монотонную revision при редактировании снимка и синхронизирует часы с полученным прогрессом. Повторная отправка того же снимка при autosave/pagehide использует прежнюю revision. Более старая версия не меняет базу: HTTP 200 `{saved:false,reason:'stale',draft,revision}` возвращает актуальный серверный снимок. Клиент восстанавливает его; завершение не сбрасывает версию черновика. Для старых клиентов без revision сервер выдаёт `max(now_ms,stored+1)`.

За новый уровень начисление происходит один раз; повторное прохождение и подсказки не отнимают баллы. За анкету, отклик, аналитику или обычную запись на событие баллы не начисляются. Обмен создаёт запись выдачи и отрицательную запись ledger в одной транзакции после проверки баланса и общего остатка. В API нет пользовательского произвольного начисления; административная корректировка создаёт отдельную компенсирующую запись с причиной и аудитом.

Ledger: `{id,reason,delta,created}`. Отклик содержит неизменяемый снимок анкеты и имеет алиасы `offer`/`offerId`, регистрация — `event`/`eventId`, обмен — `reward`/`rewardId`. Один пользователь отправляет один отклик на предложение, имеет одну запись на событие и меняет каждую награду один раз. Отменённую регистрацию можно восстановить при наличии мест.

`routeProgress` содержит шесть начальных заданий: `shift-1`, `signal-1`, `movement-1`, `lab-1`, `delivery-1`, `history-1`. `routeCompleted` позволяет показать приглашение на экскурсию; календарь доступен и до завершения маршрута.

## Игры и публикация

Стартовый контент: 15 учебных раундов в шести механиках. Четыре игры имеют по три уровня; история — один тест; исследование смены — два причинно разных варианта. Новые уровни существующей механики создаются в Unfold, добавление новой механики требует кода.

| Механика | Формат решения и серверная проверка |
| --- | --- |
| signal | `{rules:[{condition,output}]}`; порядок условий и все комбинации входного потока |
| movement | `{gears:[{x,y}],belts?:[{from:{x,y},to:{x,y}}]}`; контакт меняет направление, открытый ремень сохраняет его; разрешённые связи, границы, занятые валы, ограничения деталей и противоречивые циклы |
| lab | `{sampleId,evidence:[testId]}`; исследования должны обоснованно выделять один образец |
| delivery | `{placements:[{batchId,x,y,rotated}],route:[{x,y}]}`; точный комплект, резерв, геометрия палеты и непрерывный маршрут через партии |
| history | `{answers:{questionId:optionId}}`; закрытое соответствие опубликованной версии |
| shift | `{observedChange,explanation,evidence:[factId],nextStep,responsible}`; локализация, причина, достаточность доказательств и безопасное действие |

«Разберись в смене» содержит 12 показателей, временные ряды, схему, журнал, независимые проверки, до 32 собственных наблюдений и конструктор вывода. Перед завершением клиент сохраняет draft с выбранными наблюдениями. Сервер канонизирует известные факты, сохраняет заметки, но не оценивает их естественный язык. Принимаются разные достаточные наборы без противоречий. Первый сценарий ограничен упаковкой; во втором падает подача. В стартовых графиках причинный показатель меняется раньше последствий. За новый раунд — 30 баллов один раз, успешный ответ содержит `assessment` и `outcome`; частичная попытка баллов не даёт.

Сохранённый черновик уровня и опубликованная версия разделены. Публикация создаёт неизменяемый snapshot после проверки структуры, связей и положительных/отрицательных решений настоящим валидатором. `presentation` определяет роли спрайтов и сцену; механика остаётся в `puzzle`. Приватные правила истории/смены и проверочные решения не отправляются в публичный API. Предпросмотр использует тот же игровой рендерер, защищён сессией админки и CSRF, не выдаёт баллы. [Инструкция редактора](content-admin.md), [форматы уровней](game-levels.md), [игровые сценарии](games.md).

## Активности мероприятий и QR

Публичная активность: `{id,eventId,title,description,points,active}`. Определения хранятся в PostgreSQL `event_activities`. Для каждой новой активности автоматически создаётся уникальный токен `secrets.token_urlsafe(32)` — 43 символа URL-safe алфавита. Payload: `ochakovo:activity:v1:<opaqueToken>`. Токен не включается в Git, каталог или bootstrap участников.

Организатор создаёт и редактирует активности через Unfold. Закрытая страница QR требует права на активность и `operations.view_activity_qr`; доступны просмотр, PNG, SVG и печать. Повторное скачивание и изменение описания не меняют код; отключение активности запрещает новые выполнения. Публичного административного endpoint `/api/admin/event-activities` нет.

`POST /api/event-activities/scan` с `{code}` возвращает `{activity,event:{id,title},completion:{activityId,eventId,completedAt,awardedPoints},pointsAwarded,alreadyCompleted,balance}`. Нужны соответствующая аудитория события и профиль кандидата либо активный staff-вход. Запись на встречу не обязательна; сканирование не создаёт регистрацию и не расходует места. Это подтверждение владения QR, а не независимое доказательство физического присутствия.

Выполнение и ledger `event-activity:<id>` записываются атомарно один раз на пользователя/активность. Повтор возвращает `pointsAwarded:0`; `completion.awardedPoints` сохраняет историческую сумму после изменения стоимости. Bootstrap содержит свои `activityCompletions`. Ошибки: неверный формат/чужой QR — 400 `qr_invalid`, неизвестный — 404 `activity_not_found`, отключённый — 409 `activity_inactive`.

Клиентский сканер использует VK Code Reader, камеру/изображение через ZXing либо ручной ввод. Доступ к камере — по нажатию; потоки и object URL освобождаются при остановке. Изображения до 10 МиБ читаются локально, сервер получает только payload; сторонние ссылки не открываются.

## Материалы, аудитории и медиа

Аудитории `candidate`, `staff`, `all` проверяются сервером при получении материала, события, файла и выполнении активности. Staff-вход требует действующего аккаунта; назначенная практика не нужна сотруднику для чтения внутреннего контента. В материале показываются только публичные вопросы; правильные ответы закрыты. Версии вопросов сохраняются, completion и начисление уникальны на ID материала; каноническая история сохраняет старое начисление `history-1`.

`material_media` хранит защищённые PNG/JPEG/WebP/MP4/WebM до 50 МиБ в BYTEA. Загрузка доступна редактору через персональную форму Unfold. `GET /api/media/:id` требует bearer-сессию, подходящую аудиторию и ссылку из опубликованного неархивного материала. Закрытые файлы не копируются в public/dist; HTML и SVG upload не поддерживаются. Клиент загружает Blob целиком; потоковое хранилище/CDN не реализовано. Объём файлов входит в размер резервной копии PostgreSQL.

## Административные границы

Основная админка `/admin/` использует персональные Django-аккаунты, CSRF и модельные/операционные права. Сессия кандидата или staff-аккаунт мини-приложения не дают входа в Unfold. Рабочий стол запрашивает только разрешённые агрегаты. HR видит анкеты и рекомендации; организатор — события/QR/выдачу; координатор — практику; редакторы — содержание; технический администратор — учётные записи и диагностику. Личные опросы, карьерные предпочтения и обезличивание требуют отдельных полномочий. История и начисления не становятся произвольно редактируемыми полями. [Runbook и права](django-admin.md).

Прежний `/api/admin/*` отключён в PostgreSQL runtime и возвращает HTTP 410 `admin_api_retired`, даже при переданном старом `ADMIN_TOKEN`. Общий ключ не обходит Django RBAC. Legacy SQLite-тесты сохраняют прежний контракт только как регрессионный oracle; это не рабочий интерфейс администрирования.

Клиентская аналитика ограничена allowlist и не принимает произвольный профиль. Реферальная отметка подсвечивает отклик HR; мерч появляется только после отдельного подтверждения состоявшегося найма. Уникальность по трудоустроенному кандидату исключает несколько наград за разные заявки. [Реферальный контракт](referrals.md).

## Проверка и production

```sh
npm run build
npm test
DJANGO_TEST_DATABASE_NAME=test_ochakovo_ci .venv/bin/python manage.py test backoffice --noinput
```

Для Django-тестов нужна доступная PostgreSQL и право создания отдельной тестовой базы. `npm test` запускает также legacy-тесты во временных SQLite-файлах и TypeScript-тесты. Они не переключают runtime на SQLite. Не указывайте runtime-базу как тестовую.

Django раздаёт только допустимые файлы сборки и безопасный SPA fallback; закрытые `.data`, env, исходники и traversal-пути недоступны. Статика Unfold собирается в `.data/static` и отдаётся отдельным маршрутом `/static/`. `game-preview.html` входит в production-сборку. Admin защищён от iframe, страницы мини-приложения разрешают встраивание VK. Compose использует PostgreSQL volume, Gunicorn и Caddy; запуск, импорт и резервные копии описаны в [django-admin.md](django-admin.md) и [vk-deployment.md](vk-deployment.md). Реальный вход из VK требует настроенного приложения и отдельно проверяется в клиенте VK.

Карьерные пояснения уровня (`careerExplanation`) хранятся в `LevelDefinition.career_explanation` и неизменяемом опубликованном снимке. Срок отклика `CareerOffer.deadline` допускает 500 символов. Для явного переноса согласованных стартовых текстов без перезаписи редакторских правок используется `sync_seed_copy`; порядок описан в [runbook](django-admin.md#согласованное-обновление-стартовых-текстов).
