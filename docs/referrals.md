# Приглашения кандидатов и мерч для практикантов

Управление рефералкой уже реализовано в **Django Unfold `/admin/`**, хранилище runtime — **PostgreSQL**. Именной администратор с доменными разрешениями подтверждает найм и выдачу мерча; действия попадают в операционный аудит. Есть процесс выдачи `Fulfilment`. Ниже сохранён доменный/API-контракт; исторические `/api/admin/*` выведены из эксплуатации и возвращают `410 admin_api_retired`. Управление выполняется через именную админку. См. [Django-админку](django-admin.md), [актуальную модель](admin-entities.md) и [ORM-манифест](django-models.json).

Практикант получает персональный код и делится им с кандидатом. Кандидат указывает код при отправке отклика; в HR-списке такой отклик получает заметную отметку. Если кандидат трудоустроен, HR отдельно подтверждает этот факт, после чего практиканту создаётся право на мерч. Решение о найме остаётся за HR; автоматического ранжирования кандидатов по рефералке нет.

## Пользовательский путь

1. Активный выданный аккаунт `intern` с хотя бы одной назначенной практикой, кроме `cancelled`, открывает карточку приглашений в личном кабинете. Статусы практики `scheduled`, `active`, `completed` подходят; роли `mentor` и `employee` код не получают.
2. Сервер создаёт один стабильный код `OC-XXXXXXXX` на практиканта. Восемь символов выбираются криптографически из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`; похожие I/O/0/1 исключены. Код можно скопировать по нажатию или выделить вручную.
3. При новом отклике кандидат может заполнить необязательное поле `referralCode`. Внешние пробелы и lowercase нормализуются. Некорректный, неизвестный, отключённый или собственный код не создаёт отклик: вся транзакция отменяется. Кандидат может исправить или очистить поле.
4. В HR-списке сохраняется отметка приглашения, код и снимок имени/ID пригласившего. Обычный пользователь получает в собственном отклике только код, без чужого имени или staff ID.
5. После фактического трудоустройства HR вызывает отдельное подтверждение. Создаётся одно право на мерч со статусом `pending` на трудоустроенного кандидата, независимо от числа его откликов. Первое подтверждённое трудоустройство фиксирует получателя мерча; подтверждение другой заявки того же кандидата возвращает `409 referral_hire_already_confirmed`. Перевод отклика в `accepted` такого права не создаёт.
6. После передачи мерча HR отмечает `issued`. Повтор подтверждения трудоустройства или выдачи не создаёт вторую награду и не меняет первоначального автора/времени.

Код относится к практиканту, а атрибуция — к конкретному отклику. Кандидат вправе указать разных пригласивших при откликах на разные предложения. Повтор существующего отклика сохраняет первоначальную атрибуцию, включая отсутствие кода: backend вызывает привязку только после новой INSERT. Замена кода повторной отправкой не предусмотрена.

## Хранение и неизменяемые снимки

Три additive-таблицы добавляются без удаления старых данных:

| Таблица | Ключи | Поля и смысл |
|---|---|---|
| `referral_codes` | PK `code`; UQ/FK `user_id → users.id` | `active`, `created`; один код практиканта, отключение не генерирует замену |
| `application_referrals` | PK/FK `application_id → applications.id`; FK `code → referral_codes.code`; FK `referrer_user_id → users.id` | `referrer_name`, `created`; code/name/user ID сохраняют происхождение нового отклика |
| `referral_merch_rewards` | PK `id`; UQ/FK `application_id → application_referrals.application_id`; UQ/FK `hired_candidate_user_id → users.id`; FK `referrer_user_id → users.id` | `referrer_name`, `referral_code`, `status`, `hired_at`, `hired_by`, `issued_at`, `issued_by`; снимок основания и выдачи мерча |

У мерча CHECK статусов `pending/issued`: для pending issued-поля NULL, для issued оба заполнены. Отдельные индексы ускоряют подсчёты по пригласившему и статусу. Каскадных удалений нет.

Изменение имени, роли, активности кода или аккаунта после отклика не переписывает снимок. Уже сформированное историческое приглашение может быть основанием мерча даже после отключения кода; новое приглашение таким кодом отклоняется. Описание SKU, остатки конкретного мерча, доставка, денежная стоимость и баллы за рефералку не заведены. Таблица мерча независима от игровых rewards/exchanges/ledger.

## Действующий API

| Метод и путь | Доступ / запрос | Ответ |
|---|---|---|
| `GET /api/referrals/me` | Сессия активного назначенного практиканта | `{code,created,stats:{applications,merchPending,merchIssued}}`; только счётчики, без кандидатов |
| `POST /api/applications` | Кандидат с валидным профилем; обычный offer ID и `referralCode?` | `application.referral:null\|{code}`, `alreadyApplied`; повтор не меняет атрибуцию |
| `GET /api/admin/applications` | HR-ключ | `referral:null\|{code,referrerUserId,referrerName,created}` на отклике |
| `POST /api/admin/applications/:id/hire` | HR-ключ, отдельное явное подтверждение | `{reward,alreadyConfirmed}`; отсутствие приглашения — `409 referral_missing` |
| `GET /api/admin/referral-rewards` | HR-ключ | `{rewards:[RewardDTO]}` |
| `PATCH /api/admin/referral-rewards/:id` | HR-ключ; `{status:'issued'}` | `{reward,alreadyIssued}`; другие переходы не принимаются |

`RewardDTO`: `id,applicationId,hiredCandidateUserId,referrerUserId,referrerName,code,status,hiredAt,hiredBy,issuedAt,issuedBy`. Actor задаёт сервер (`hr-admin` при текущем общем HR-ключе); произвольный actor из тела запроса не используется. Это отметка операции, а не полноценная система именных администраторских аккаунтов.

Формат кода — `422 referral_invalid`; неизвестный/недоступный код — одинаковый `422 referral_unavailable`; собственный — `422 referral_self`. В этих ошибках нет имени, контакта или ID пригласившего. Неподходящий аккаунт для получения своего кода — `403 referral_forbidden`. Код приглашения не является авторизационным секретом и не открывает чужой профиль.

## Граница серверного модуля

`server/referrals.py` не делает commit и не проверяет HTTP-ключ администратора: аутентификация и транзакция находятся в корневом router. Его функции:

- `migrate(db)` — additive SQL-схема.
- `get_or_create_code(db,uid)` — собственный код и анонимные счётчики.
- `bind_application(db,uid,application_id,code)` — только для новой INSERT того же пользователя в той же транзакции.
- `referral_for_application(db,id,admin=False)` и plural helper — сериализация уже разрешённых вызывающему откликов.
- `mark_hired(db,application_id,actor='hr-admin')`, `mark_reward_issued(db,id,actor='hr-admin')`, `merch_rewards(db)` — только из защищённого HR-router.

В действующем runtime используется атомарная транзакция Django/PostgreSQL; `BEGIN IMMEDIATE` относится к сохранённому SQLite-тестовому baseline. Уникальные application ID и hired candidate user ID в праве на мерч защищают однократность: несколько заявок одного кандидата не создают несколько наград, в том числе при конкурентном подтверждении. Генерация кодов проверяет уникальность и повторяет криптографический выбор при коллизии.

## Админка и дальнейшие расширения

Unfold поддерживает HR-просмотр приглашений, явное подтверждение найма, выдачу мерча, именные права и операционный аудит. Компенсирующий процесс отмены ошибочного найма, полноценный физический склад SKU и интеграция доставки остаются расширениями. Они не подменяются автоматическим принятием отклика или начислением игровых баллов.

Проверки модуля находятся в `server/tests/test_referrals.py`: стабильность и коллизии кодов, роли/назначения, формат/неизвестный/неактивный/собственный код, privacy, транзакционный rollback, снимки и повторы, отсутствие мерча от accepted, явное подтверждение/выдача, несколько откликов одного кандидата и конкурентная однократность.
