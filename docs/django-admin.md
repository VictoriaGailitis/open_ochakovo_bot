# Django Unfold: запуск и эксплуатация

Основная админка находится по `/admin/`. Она работает в том же Django/PostgreSQL runtime, что и мини-приложение. Django-аккаунты администраторов отделены от VK, демонстрационных пользователей и аккаунтов сотрудников мини-приложения. Прежний общий `/api/admin/*` возвращает `410 admin_api_retired`; старый токен не даёт обхода персональных прав.

## Локальная подготовка

Нужны Python 3.13, Node.js 22+, npm и работающий Docker. Команды выполняются из корня проекта:

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/setup-local.py
npm ci
npm run dev
```

`setup-local.py` создаёт именованный контейнер `open_ochakovo_postgres` с PostgreSQL 16, volume `open_ochakovo_pgdata` и loopback-портом 55432. Случайный пароль находится только в игнорируемых `.data/postgres.env` и `.env`; существующие файлы не перезаписываются. При отсутствии production secret локальная настройка `DEV_AUTH=1` позволяет создать `.data/django-secret` с правами 0600.

`npm run dev` сначала выполняет `scripts/prepare_dev.py`:

1. Применяет миграции Django.
2. При наличии совместимой `.data/ochakovo.sqlite3` и отсутствии пользователей запускает безопасный импорт. Импорт дополнительно требует пустоты всех целевых legacy-таблиц.
3. Выполняет `bootstrap_miniapp`: добавляет отсутствующие определения, стартовые публикации и исторические факты согласия. Редакторские изменения и пользовательские результаты не заменяются.
4. При локальных `DEV_AUTH=1` и DEBUG создаёт отдельного администратора для разработки.

Адреса: мини-приложение — http://127.0.0.1:5188; API и админка — http://127.0.0.1:3001/admin/. Логин и случайный пароль локального администратора находятся в `.data/django-local-admin.json`, который не входит в Git. Команда не выводит пароль в журнал и не сбрасывает существующий аккаунт. Этот файл не переносится в production.

Для повторной подготовки без запуска серверов используйте `npm run admin:prepare`. Для проверки собранного интерфейса: `npm run build`, затем `npm start`. Это development server Django; production использует Gunicorn. Подготовка не удаляет PostgreSQL volume и не выполняет `flush`.

## Настройки и персональные аккаунты

Django читает `.env`; явно переданные переменные процесса имеют приоритет. Обязательны `DATABASE_URL` с PostgreSQL и Django `SECRET_KEY` длиной не менее 50 символов. При `DEV_AUTH=0` локальный secret автоматически не создаётся. Справочник переменных — [backend.md](backend.md#настройки), production пример — `.env.production.example`.

В production после миграций создайте персонального администратора интерактивно:

```sh
docker compose --env-file .env.production exec app python manage.py createsuperuser
```

При запуске без Docker:

```sh
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py bootstrap_miniapp
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/python manage.py createsuperuser
```

Последние команды используют текущую приватную конфигурацию PostgreSQL. Production-сервер должен иметь `DEV_AUTH=0`, `DJANGO_DEBUG=0`, корректные `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` и HTTPS. За доверенным Caddy Compose включает `DJANGO_TRUST_PROXY=1`; прямой публичный доступ к порту Gunicorn отсутствует.

Суперпользователь создаёт отдельные Django User для членов команды, включает `is_staff` и назначает нужные группы. Аккаунты не создаются при настройке ролей. Штатные Django User/Group имеют оформление Unfold и требуют отдельных разрешений `auth.*`; HR, организатор и редактор не получают их автоматически.

## Роли и границы доступа

```sh
.venv/bin/python manage.py setup_backoffice_roles
```

Для контейнера добавьте префикс `docker compose --env-file .env.production exec app python` вместо `.venv/bin/python`. Команда идемпотентно приводит разрешения именованных групп к описанному в коде набору; ручные дополнения к этим группам при повторном запуске будут заменены. Назначайте специальные полномочия пользователю или отдельной группе.

| Группа | Рабочие действия |
| --- | --- |
| `HR` | Анкеты и снимки откликов, статусы, реферальные отметки, подтверждение состоявшегося найма, история согласий |
| `organizer` | Мероприятия, активности, приватные QR, записи и организация выдачи наград |
| `coordinator` | Практики, наставники, назначения, цели, встречи и обращения координатору |
| `technical_admin` | Выданные аккаунты мини-приложения, отзыв сессий, диагностика, аудит и компенсирующие записи баллов |
| `content_editor` | Материалы, тесты, защищённые медиа, карьерные предложения и награды |
| `game_editor` | Семейства, уровни, закрытые правила, спрайты, модули, объекты сцены и публикация |

Права на личные добровольные опросы, карьерные предпочтения и обезличивание назначаются отдельно. Наличие технической роли не даёт чтения ФИО и контактов анкеты. Рабочий стол выполняет только разрешённые запросы агрегатов: отклики/рефералка для HR, события для организатора, материалы/уровни для редактора. Профили, содержимое опросов и пользовательские ID в его счётчики не включаются.

Исторические начисления, версии, результаты и снимки не редактируются как обычные формы. Административные изменения оставляют аудит. Исправление анкеты требует основания; согласие и обезличивание выполняются отдельными действиями. Отзыв сессий и выдача staff-аккаунтов не изменяют пароли персональных Django-аккаунтов.

## Материалы, тесты и уровни

Редактор материала собирает заголовки, текст, изображения и видео, выбирает аудиторию и публикацию. Защищённые файлы загружаются через форму медиа: PNG/JPEG/WebP/MP4/WebM до 50 МиБ; файл хранится в PostgreSQL. Конструктор теста поддерживает вопросы, варианты, правильные ответы, пояснения и баллы. Каждое сохранение создаёт новую версию; старые прохождения и выданные баллы сохраняются. Пустой тест явно оформляется как материал без теста. Публичный API не передаёт правильные ответы.

В редакторе игр выбирается одна из шести существующих механик. Условия, спрайты, слоты модулей и сцена настраиваются декларативно. Для истории и смены добавляется закрытое правило; для публикации нужны корректные положительные и отрицательные проверочные решения. Предпросмотр использует тот же React-рендерер, проверяет ответы без начисления баллов и требует сессию админки с CSRF. Изменение черновика не меняет опубликованную версию. Добавление новой механики требует кода.

Подробный путь редактора — [content-admin.md](content-admin.md). Поля и связи — [admin-entities.md](admin-entities.md).

## Мероприятия, QR и выдача

Организатор создаёт мероприятие, задаёт аудиторию, дату, место и вместимость. Уменьшение вместимости не должно исключать уже зарегистрированных участников: форма проверяет занятые места. Внутри мероприятия добавляются активности с названием, описанием и баллами. Токен QR создаётся сервером автоматически, не вводится вручную и остаётся стабильным при изменении описания.

Ссылка активности открывает закрытую страницу QR: предпросмотр, скачивание PNG/SVG и печать. Нужны права на активность и `operations.view_activity_qr`. Повторная загрузка QR не перевыпускает код. Деактивация запрещает новые выполнения; история и начисленные суммы сохраняются. QR не является доказательством физического присутствия и не создаёт регистрацию на мероприятие.

Обычный обмен баллов и реферальный мерч имеют отдельный учёт выдачи. По рефералке право возникает только после явного подтверждения HR, что кандидат действительно трудоустроен; смена статуса отклика сама этого не делает. Один кандидат создаёт одно право на мерч даже при нескольких заявках. Выдача сохраняет исполнителя и время, баллы за рефералку не начисляются.

## Перенос старого прототипа

Импорт выполняется **до bootstrap и первого обычного запуска** на пустые 31 целевую таблицу core. Django migrations сначала создают схему, но не заполняют доменные таблицы. Если bootstrap уже был выполнен, используйте отдельную пустую PostgreSQL-базу; команда не содержит режима перезаписи или очистки.

Исходный согласованный SQLite snapshot храните приватно. Пример ручного локального переноса:

```sh
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py import_sqlite --source .data/legacy-import.sqlite3 --dry-run
.venv/bin/python manage.py import_sqlite --source .data/legacy-import.sqlite3
.venv/bin/python manage.py bootstrap_miniapp
```

Убедитесь, что `DATABASE_URL` указывает на нужную **пустую** целевую базу, прежде чем выполнять команды. Исходный файл открывается `mode=ro`; importer проверяет наличие всех таблиц/столбцов и старые FK, количество строк и итоговые ограничения. Реальный импорт создаёт согласованную SQLite-копию с SHA256 в `.data/migration-backups/`, затем переносит данные одной транзакцией. `--dry-run` выполняет проверки и откат, без резервной копии. `--backup-dir` позволяет задать приватный каталог копии.

Старые логические ссылки на мероприятия без определения сохраняются как неопубликованные архивные заглушки, чтобы не потерять регистрации и активности. Прежние ID, QR-токены, начисления, снимки и рефералка сохраняются; технические последовательности PK синхронизируются. Источник не изменяется. Любая непустая целевая legacy-таблица приводит к отказу, а не слиянию. Несовместимую старую схему сначала обновляют средствами соответствующего прототипа на отдельной копии.

Для переноса в Compose сначала поднимите только `db`, соберите образ, выполните `migrate` и `import_sqlite` через одноразовый `docker compose run ... app python manage.py ...`, переопределив штатный CMD. Исходный согласованный snapshot подключите read-only и обеспечьте чтение контейнерному UID 10001; резервная копия создаётся в постоянном `/app/.data`. Только после успешного импорта запускайте обычный `app`, который выполнит bootstrap. Пример последовательности приведён в [VK-размещении](vk-deployment.md#перенос-существующей-sqlite-базы).

## Резервные копии PostgreSQL

В локальном режиме данные находятся в `open_ochakovo_pgdata`, в production Compose — в volume `postgres_data` проекта. `.data` больше не является основной базой. Пересоздание контейнера сохраняет volume; `docker compose down -v` удаляет его и не используется для обновления.

Согласованная логическая копия production-базы:

```sh
mkdir -p backups
chmod 700 backups
umask 077
docker compose --env-file .env.production exec -T db pg_dump -U ochakovo -d ochakovo -Fc > backups/ochakovo.dump
```

Имя файла меняйте для хранения нескольких поколений. Dump включает профили, историю, содержимое, медиа и приватные токены; храните его за пределами публичного репозитория и копируйте в защищённое отдельное хранилище. Для полного восстановления также нужны приватная конфигурация окружения и сохранённые volumes Caddy; их не кладут в Git.

Проверка восстановления делается в **отдельную пустую базу**, не поверх рабочей:

```sh
docker compose --env-file .env.production exec -T db createdb -U ochakovo ochakovo_restore
docker compose --env-file .env.production exec -T db pg_restore -U ochakovo -d ochakovo_restore --no-owner --no-acl < backups/ochakovo.dump
```

Затем проверьте количество записей, миграции и критические сценарии на отдельном экземпляре приложения. Автоматическое расписание, внешнее хранилище и восстановление на момент времени этим репозиторием не настраиваются; оператор должен организовать их для production.

## Обновление и проверка

```sh
npm run build
npm test
DJANGO_TEST_DATABASE_NAME=test_ochakovo_ci .venv/bin/python manage.py test backoffice --noinput
```

Django-тесты работают на отдельной PostgreSQL-базе; роли БД нужно право её создания. Не задавайте имя рабочей базы как тестовое. Старые доменные тесты SQLite — только regression oracle. Для production перед обновлением сделайте backup, затем выполните `docker compose --env-file .env.production up -d --build`: entrypoint применит migrations, добавит отсутствующий seed и соберёт статику. Обычные изменения содержимого через админку не требуют сборки фронтенда.

Проверяйте вход каждой роли, недоступность чужих разделов, сохранение черновика/публикации, однократные баллы, запись с лимитом мест и работу QR после перезапуска. Реальную авторизацию VK и публичный TLS нужно дополнительно проверить в целевом окружении; локальные тесты этого не подтверждают.
